# AGENTS.md — Инструкции для AI-агента

## 1. Общие сведения о проекте

Проект разрабатывается на языке C++.

- **Язык:** C++17 / C++20 / C++23 (используй стандарт, установленный в проекте).
- **Система сборки:** CMake.
- **Основные приоритеты:** корректность, надёжность, читаемость, сопровождаемость и производительность.
- **Главный принцип:** любое изменение должно быть обоснованным, минимальным и соответствовать существующей архитектуре.

Перед выполнением задачи изучи соответствующий код, структуру проекта, настройки сборки и существующие тесты.

Не делай предположений о реализации, если информацию можно проверить в репозитории.

## 2. Основные принципы разработки

1. **Простота важнее сложности.** Предпочитай понятные решения сложным абстракциям.
2. **Минимальные изменения.** Меняй только то, что необходимо для выполнения задачи.
3. **Соблюдение архитектуры.** Используй существующие подходы и соглашения проекта.
4. **Устранение первопричин.** Исправляй причину проблемы, а не маскируй её последствия.
5. **Отсутствие лишнего рефакторинга.** Не изменяй несвязанный код без необходимости.
6. **Обратная совместимость.** Не нарушай существующие публичные интерфейсы без явного требования.
7. **Предсказуемость.** Код должен иметь понятное поведение, включая ошибки и граничные случаи.
8. **Обоснованная оптимизация.** Не усложняй код ради предполагаемого прироста производительности без измерений.

Не добавляй новые зависимости, архитектурные слои, универсальные обёртки или шаблонные конструкции без реальной необходимости.

## 3. Правила написания C++ кода

### 3.1. Стиль и современные возможности C++

- Используй стандарт C++, установленный в проекте.
- Соблюдай существующие соглашения об именовании и форматировании.
- Если в проекте есть `.clang-format`, следуй его настройкам.
- Предпочитай стандартную библиотеку собственным реализациям, когда это оправданно.
- Используй `const`, `constexpr` и `noexcept` там, где это корректно и полезно.
- Используй `enum class` для новых перечислений, если нет причин использовать обычный `enum`.
- Избегай макросов, если задачу можно решить средствами языка.
- Не вводи шаблоны, наследование и полиморфизм без необходимости.
- Не применяй новые возможности языка исключительно ради их использования.
- Сохраняй стиль окружающего кода, если он не противоречит требованиям безопасности и корректности.

### 3.2. Управление памятью и временем жизни объектов

- Следуй принципам RAII.
- Предпочитай автоматическое управление временем жизни ресурсов.
- По возможности используй семантику значений.
- Для исключительного динамического владения используй `std::unique_ptr`.
- Используй `std::shared_ptr` только при действительно совместном владении.
- Не применяй ручные `new` и `delete` без необходимости.
- Явно учитывай владение объектами и их время жизни.
- Не возвращай указатели, ссылки или представления на уничтоженные объекты.
- Избегай ненужных динамических выделений памяти.
- Не допускай утечек памяти, двойного освобождения и обращения к освобождённой памяти.

### 3.3. Корректность и безопасность

- Инициализируй переменные перед использованием.
- Не допускай неопределённого поведения (undefined behavior).
- Избегай небезопасных преобразований типов.
- Проверяй внешние данные на соответствующих границах системы.
- Обрабатывай ошибки согласованно с архитектурой проекта.
- Не игнорируй ошибки без обоснования.
- Соблюдай гарантии безопасности исключений, если исключения используются.
- Учитывай переполнение целых чисел, выход за границы контейнеров и некорректное время жизни объектов.
- Не изменяй поведение обработки ошибок без необходимости.

### 3.4. Многопоточность

При работе с многопоточным кодом:

- Не допускай гонок данных (data races).
- Минимизируй совместно изменяемое состояние.
- Соблюдай существующую модель синхронизации.
- Учитывай порядок захвата блокировок.
- Не добавляй блокировки без анализа возможных взаимных блокировок (deadlocks).
- Не применяй атомарные операции без понимания требований к порядку памяти.
- Не изменяй модель конкурентного выполнения без обоснования.
- Учитывай время жизни объектов, используемых несколькими потоками.

### 3.5. Заголовочные файлы и интерфейсы

- Сохраняй публичные интерфейсы минимальными.
- Не раскрывай внутренние детали реализации без необходимости.
- Избегай лишних зависимостей между заголовочными файлами.
- Используй предварительные объявления там, где это допустимо и полезно.
- Не добавляй `using namespace` в заголовочные файлы.
- Избегай нарушения ODR (One Definition Rule).
- Учитывай совместимость API и ABI, если она важна для проекта.

## 4. Изучение кодовой базы

Перед внесением изменений:

1. Найди соответствующий модуль и связанные компоненты.
2. Изучи заголовочные файлы и реализации.
3. Найди аналогичные решения в существующем коде.
4. Изучи связанные тесты.
5. Проверь используемые зависимости и настройки сборки.
6. Определи ограничения архитектуры.
7. Выбери минимальное изменение, решающее задачу.

Не придумывай несуществующие классы, функции, файлы, цели сборки или API.

Если в проекте уже существует подходящая реализация, предпочитай её созданию новой.

## 5. Сборка и проверка кода

Используй команды сборки, принятые в проекте.

Пример для CMake (адаптируй под фактическую конфигурацию):

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
```

После изменений:

- Собери затронутые компоненты.
- Запусти соответствующие тесты.
- По возможности проверь сборку всего проекта.
- Выполни форматирование согласно правилам проекта.
- Используй статический анализ, если он настроен.
- При необходимости проверь код с помощью санитайзеров.

Не изменяй глобальные настройки компиляции только ради устранения локальной проблемы.

Не утверждай, что сборка или тестирование прошли успешно, если они не были выполнены.

Если проверка невозможна, объясни причину.

## 6. Требования к тестированию

- При исправлении ошибок по возможности добавляй регрессионные тесты.
- При добавлении нового поведения дополняй существующие тесты.
- Проверяй граничные условия и ошибочные сценарии.
- Предпочитай детерминированные тесты.
- Не создавай зависимость от случайных задержек или порядка выполнения потоков без необходимости.
- Не удаляй и не отключай тесты ради успешного прохождения проверок.
- Разделяй ранее существовавшие ошибки и регрессии, внесённые текущими изменениями.

Для кода, работающего с памятью и потоками, при наличии соответствующей инфраструктуры используй:

- AddressSanitizer (ASan).
- UndefinedBehaviorSanitizer (UBSan).
- ThreadSanitizer (TSan).

Учитывай совместимость выбранных инструментов и ограничения окружения.

## 7. Производительность

При изменении критичных участков кода:

- Избегай ненужных выделений памяти.
- Не копируй большие объекты без необходимости.
- Учитывай вычислительную сложность алгоритмов.
- Сохраняй существующие требования к задержкам и использованию памяти.
- Не добавляй кэширование без анализа инвалидирования и потокобезопасности.
- Избегай преждевременной оптимизации.
- По возможности подтверждай улучшения бенчмарками.

Корректность имеет приоритет перед недоказанным приростом производительности.

## 8. Порядок выполнения задач

Для каждой задачи придерживайся следующего процесса:

1. **Понимание.** Определи цель и ожидаемый результат.
2. **Исследование.** Найди связанные файлы, зависимости и тесты.
3. **Анализ.** Определи причину проблемы или подход к реализации.
4. **Планирование.** Для нетривиальных изменений составь краткий план.
5. **Проверка.** Собери изменённые компоненты и выполни доступные проверки.
6. **Самопроверка.** Изучи итоговый diff и убедись, что нет посторонних изменений.
7. **Отчёт.** Кратко опиши результат, проверки и оставшиеся риски.

Если задача затрагивает неоднозначные архитектурные решения, запроси уточнение перед внесением масштабных изменений.

Для небольших и очевидных исправлений не создавай избыточный план.

## 9. Ограничения для AI-агента

### 9.1. Обязательные действия

- Соблюдай архитектуру и соглашения проекта.
- Проверяй существующие реализации перед созданием новых.
- Не вноси изменения в код или любой файл проекта без явного разрешения. Всегда спрашивай, можно ли внести изменения в файлы.
- Учитывай пользовательские изменения в рабочем дереве.
- Обосновывай важные технические решения.
- Сообщай реальные результаты сборки и тестирования.
- Явно указывай допущения и непроверенные сценарии.

### 9.2. Требуется предварительное согласование

- Добавление сторонних библиотек.
- Изменение публичных API или ABI.
- Изменение форматов сериализации и сохраняемых данных.
- Существенные изменения архитектуры.
- Изменение модели многопоточности и синхронизации.
- Изменение глобальных флагов компилятора.
- Рефакторинг.
- Удаление частей существующего кода.
- Любые изменения существующего кода и/или существующих файлов.

### 9.3. Запрещённые действия

- Не изменяй файлы, не связанные с задачей, без обоснования.
- Не изменяй внешнее поведение программы незаметно для пользователя.
- Не скрывай ошибки отключением проверок или предупреждений.
- Не удаляй тесты для маскировки проблем.
- Не перезаписывай пользовательские изменения.
- Не выполняй `git commit`, `git push` и создание Pull Request без явного разрешения.
- Не заявляй об успешных тестах или измерениях, которые не проводились.
- Не вноси масштабные изменения только ради улучшения стиля.
- Не добавляй ненужные комментарии, абстракции или вспомогательные функции.

## 10. Формат итогового ответа

После выполнения задачи предоставь краткий технический отчёт.

### Изменения
- Какие компоненты изменены.
- Что реализовано или исправлено.
- Почему выбран данный подход.

### Проверки
- Какие команды выполнялись.
- Какие тесты пройдены.
- Какие проверки не удалось выполнить.

### Риски и ограничения
- Известные ограничения.
- Непроверенные сценарии.
- Важные допущения.

Ответ должен быть технически точным, кратким и не содержать неподтверждённых утверждений.
